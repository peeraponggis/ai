# 02 — ทฤษฎีการบริหาร → ระบบกำกับดูแลโมเดล (Model Governance)

> ที่มา: `ทฤษฎีการบริหารและแก้ปัญหาการทำงาน.docx` (ไฟล์จากผู้ใช้ 2026-08-23, 470 ย่อหน้า)
> เอกสารต้นทางมี 3 ส่วน: ทฤษฎีบริหารทั่วไป · blueprint ระบบโซลาร์ · สถาปัตยกรรม multi-agent
> เอกสารนี้แปลงทั้งหมดเป็น **กฎการทำงานของระบบโมเดล** ที่ตรวจสอบได้

## 1. สาระจากต้นฉบับ

| กลุ่ม | เครื่องมือ | ใช้ตอบคำถามว่า |
|---|---|---|
| ตรวจสอบความสำเร็จ | **KPI · OKR · Balanced Scorecard** (4 มิติ: Financial / Customer / Internal Process / Learning & Growth) | งานสำเร็จหรือยัง วัดจากอะไร |
| ขับเคลื่อนงาน | **PDCA · DMAIC** (Define–Measure–Analyze–Improve–Control) | จะทำให้สำเร็จตามระบบได้อย่างไร |
| เสนอทางเลือก | **5 Whys · Fishbone · SWOT · Decision Matrix** | จะเลือกทางแก้ไหน ด้วยเหตุผลอะไร |

ส่วนที่เป็น AI: blueprint 5–6 stage (ingest → sizing → financial → proposal → human-in-the-loop →
multi-agent consensus), การเปรียบเทียบโมเดลฟรีกับเสียเงิน, และสถาปัตยกรรม
**Debate & Consensus** ที่กำหนดบทบาท (persona) ให้แต่ละโมเดล: Technical / Financial / Risk
แล้วมี **Aggregator (The Judge)** สรุป

## 2. DMAIC = วงจรปฏิบัติการของระบบโมเดล

นี่คือการจับคู่ที่มีค่าที่สุด เพราะสิ่งที่เราสร้างมาแล้วเข้ากับ DMAIC พอดีทุกขั้น

| ขั้น | ในบริบทระบบโมเดล | ของจริงที่มีแล้ว |
|---|---|---|
| **Define** | ระบุว่าจะให้โมเดลทำงานอะไร และเกณฑ์รับ/ไม่รับคืออะไร | เกณฑ์ 4 ข้อในเอกสาร 02 (ชนะโมเดลเดี่ยวแบบ CI ไม่ทับ, Brier ดีขึ้น ≥30%, ECE ≤0.05, อยู่ในงบ request) |
| **Measure** | วัด baseline ก่อนปรับปรุงเสมอ | `p` + Wilson CI, `φ`, double-fault, Brier/ECE — `analyze.py` |
| **Analyze** | หา root cause ของความผิดพลาด ไม่ใช่แก้ที่อาการ | 5 Whys กับข้อที่ตอบผิด + แยกผลตามหมวด (numeric/extract/classify) |
| **Improve** | เปลี่ยนชุดโมเดล / prompt / วิธีรวมคำตอบ แล้ววัดซ้ำ | เปลี่ยน provider config → ยิงใหม่ → เทียบ |
| **Control** | ล็อกผลไว้ ไม่ให้ถอยกลับ | re-probe ก่อนวัดทุกครั้ง + เก็บ `raw_answers.jsonl` ไว้ทุกรอบ |

### ตัวอย่าง Analyze ด้วย 5 Whys จากข้อผิดพลาดจริง

`mistral-Nemo` ตอบ `100,000 ÷ 5 = 2000` (ผิด 10 เท่า)

1. ทำไมผิด → คำนวณเลขผิดหลัก
2. ทำไมคำนวณผิด → โมเดลภาษาไม่ได้คำนวณ แต่ทำนายโทเคนถัดไป
3. ทำไมถึงปล่อยให้โมเดลคำนวณ → เพราะโจทย์ถูกส่งเป็นข้อความล้วน
4. ทำไมส่งเป็นข้อความล้วน → เพราะยังไม่มีชั้นแยกงานคำนวณออกจากงานภาษา
5. ทำไมยังไม่มี → **นี่คือ root cause** → ต้องมีชั้น L1/L2 ตามเอกสาร 04-frameworks/01

**สิ่งที่แก้จึงไม่ใช่ "เปลี่ยน prompt" หรือ "ตัดโมเดลนี้ทิ้ง" แต่คือการห้ามโมเดลคำนวณทั้งระบบ**
— ตรงกับหลักการของ Fishbone ที่ให้แยกสาเหตุเชิงระบบ (Process) ออกจากสาเหตุเฉพาะหน้า (Material)

## 3. Balanced Scorecard สำหรับระบบโมเดล

BSC บังคับให้ไม่วัดแค่มิติเดียว — ระบบ AI มักถูกวัดแค่ "แม่นแค่ไหน" ซึ่งไม่พอ

| มิติ BSC | ตัวชี้วัดของระบบโมเดล | เกณฑ์ที่เสนอ |
|---|---|---|
| **Financial** | ต้นทุนต่อการวิเคราะห์ 1 ครั้ง | 0 บาท (ข้อบังคับของโปรเจกต์นี้) |
| **Customer** | ความแม่นบนงานที่ผู้ใช้ทำจริง + ความมั่นใจที่ calibrate แล้ว | ECE ≤ 0.05 |
| **Internal Process** | uptime ของ provider, เวลาต่อ request, อัตรา error | ต้องบันทึกทุกรอบ (probe) |
| **Learning & Growth** | จำนวนโมเดลใหม่ที่ทดสอบ, φ ที่ลดลงเมื่อเพิ่มความหลากหลาย | re-probe อย่างน้อยทุกครั้งก่อนวัด |

**เหตุผลที่ต้องมีมิติ Internal Process**: บทเรียนจริงของโปรเจกต์นี้คือ **โมเดลตายโดยไม่บอกล่วงหน้า**
(`deepseek-r1`, `gpt-4o-mini` ตายทั้งคู่ · Pollinations ปิด API) ถ้าวัดแค่ความแม่น จะไม่เห็นความเสี่ยงนี้เลย

## 4. Decision Matrix สำหรับเลือกชุดโมเดล

ต้นฉบับเสนอ Decision Matrix ไว้เป็นเครื่องมือเลือกทางแก้ — นำมาใช้กับการเลือกโมเดลโดยตรง

| เกณฑ์ | น้ำหนัก | เหตุผล |
|---|---|---|
| p บนหมวดงานที่จะใช้จริง | 30% | ต้องเกิน 0.5 ก่อนถึงจะพิจารณา (เอกสาร 01 ข้อ A1) |
| **φ ต่ำ (ต่างค่ายกัน)** | **30%** | ตัวกำหนดเพดานของทั้งระบบ |
| ความเสถียร (error rate) | 20% | โมเดลที่ล่มบ่อยทำให้ทั้ง pipeline พัง |
| ความเร็ว | 10% | จำกัดจำนวนวิธีที่ใช้ได้ (debate หลายรอบแพงมาก) |
| ความยาวคำตอบ/ต้นทุนโทเคน | 10% | กระทบ rate limit |

**จุดที่ต่างจากสัญชาตญาณ**: น้ำหนักของ φ เท่ากับ p — เพราะโมเดลเก่ง 5 ตัวที่ผิดเหมือนกัน
ให้ผลแย่กว่าโมเดลกลาง ๆ 3 ตัวที่ผิดคนละแบบ

## 5. จุดที่ต้นฉบับต้องปรับตามข้อมูลใหม่

ต้นฉบับเขียนไว้ก่อนที่เราจะวัดจริง มี 3 ข้อที่ข้อมูลของเราขัดแย้ง — บันทึกไว้เพื่อไม่ให้ระบบ
ถูกออกแบบบนสมมติฐานที่ตกยุคแล้ว

| ต้นฉบับระบุ | ผลวัดจริง (2026-08-23) | ผลต่อการออกแบบ |
|---|---|---|
| ใช้ `DeepSeek-R1` เป็น Agent การเงินสาย reasoning | `deepseek-r1` คืน **400 model_unavailable** | ต้องผูกกับ `/v1/models` ที่ probe ได้จริง ไม่ผูกกับชื่อโมเดลตายตัว |
| โมเดลฟรี "รุ่น 70B ขึ้นไป" ให้ผลใกล้เคียงโมเดลเสียเงิน | ไม่มีรุ่น 70B ให้ใช้ฟรีเลย ที่ได้คือ 8B–24B และ flash-tier | ความคาดหวังต้องลดลง หรือชดเชยด้วยการรวมหลายตัว |
| แบ่ง persona (Technical/Financial/Risk) ให้โมเดลต่างตัว | ยังไม่รู้ว่า 7 โมเดลนี้ผิดพร้อมกันหรือไม่ | **persona ไม่ได้ทำให้ error decorrelate** ถ้า backend เดียวกัน ต้องวัด φ ก่อนจึงจะรู้ว่าสถาปัตยกรรมนี้คุ้มไหม |

> ประเด็นเรื่อง Learning ในต้นฉบับถูกต้องและสำคัญ: **RAG (Context Learning) กับ fine-tuning
> เป็นคนละเรื่อง** — โมเดลฟรีได้ประโยชน์จาก RAG เต็มที่ แต่ไม่ได้ทำให้ "ฉลาดขึ้น" ในเชิงน้ำหนักโมเดล
> ข้อนี้สอดคล้องกับเอกสาร 01: การรวมหลายโมเดลช่วยได้ก็ต่อเมื่อแต่ละตัวเก่งกว่าการเดา

## 6. SOP ที่ได้จากทั้งหมดนี้ (ขั้น Control)

ทุกครั้งที่จะใช้ระบบโมเดลวิเคราะห์งานจริง ต้องผ่านลำดับนี้:

1. **re-probe** provider ก่อนเสมอ — โมเดลตายเงียบ ๆ ได้ทุกวัน
2. **คัดโมเดล** ด้วย Decision Matrix ข้อ 4 (ตัดตัวที่ขอบบน CI ไม่ถึง 0.5 ออกก่อน)
3. **แยกงาน L1/L2/L3** — โค้ดคำนวณ, โมเดลอ่าน/อธิบาย, คนตัดสิน
4. **ตรวจ gate ข้อมูลขั้นต่ำ** ตามเอกสาร 04-frameworks/01 ข้อ 3 ก่อนคืนตัวเลขใด ๆ
5. **รายงานความมั่นใจที่ calibrate แล้วเท่านั้น** ห้ามใช้สัดส่วนเห็นพ้องดิบ
6. **เก็บ raw output ทุกครั้ง** เพื่อวิเคราะห์ย้อนหลังได้โดยไม่ต้องยิงซ้ำ
