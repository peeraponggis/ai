## 1. Blueprint กำหนดอะไรไว้

**Pipeline 5 stage**: Ingestion & Parsing → Sizing (pvlib) → Financial (NPV/IRR/Payback/DSCR)
→ Auto-Correction (3 ทางเลือก) → Human-in-the-Loop + Learning Loop

**ค่าตั้งต้นที่ระบุชัด**

| พารามิเตอร์ | ค่าใน Blueprint |
|---|---|
| EPC | 22 บาท/วัตต์ (ปรับตามขนาดโครงการ) |
| ค่าไฟ | 4.7 บาท/หน่วย (ไม่รวม VAT 7%) |
| Discount rate | **6.5%** (อิงดอกเบี้ยธนาคาร) |
| อายุโครงการ | 25 ปี |
| เกณฑ์ขนาด C&I | ≥ 100 kWp |
| Trigger auto-correction | Payback > 5 ปี |
| ESS ใน Option B | 200 kWh |
| EPC ใน Option A | 20.5 บาท/วัตต์ |

**Tech stack**: LangGraph/LlamaIndex · Claude 3.5 Sonnet / GPT-4o หรือ self-hosted DeepSeek-R1 / Llama 3.1 70B
· FastAPI + `pvlib-python` + `numpy-financial` · PostgreSQL (JSONB)

**Multi-Agent**: 3 agent (Technical / Financial / Risk) → Aggregator → **ลูป critique เมื่อพบข้อขัดแย้งตัวเลข**

## 3. เทียบกับผลวัดจริงของโมเดลฟรี — 3 จุดที่ Blueprint ใช้ไม่ได้ตามที่เขียน

| Blueprint ระบุ | ผลวัดจริง (2026-08-23) | ทางออก |
|---|---|---|
| LLM Core: Claude 3.5 Sonnet / GPT-4o | ทุกตัวคืน **401 invalid_api_key** ในชั้นฟรี | ใช้ได้เฉพาะเมื่อยอมจ่าย — ถ้าต้องฟรี ต้องออกแบบด้วย 7 โมเดลที่มี |

## 4. ช่องโหว่ของ Blueprint ที่ต้องอุดก่อนนำไปเขียนโค้ด

### 4.1 DSCR ไม่มีข้อมูลนำเข้าเพียงพอ

Blueprint ให้ DSCR เป็น output แต่ **Stage 3 ไม่ได้รับพารามิเตอร์เงินกู้เลย**
DSCR = กระแสเงินสดจากการดำเนินงาน ÷ ภาระหนี้ต่องวด ต้องมีอย่างน้อย:
อัตราดอกเบี้ย · ระยะเวลากู้ · สัดส่วนเงินกู้ต่อทุน (LTV) · รูปแบบการผ่อน

→ ถ้าไม่เติม 4 ค่านี้ DSCR ที่ได้จะเป็นตัวเลขที่ไม่มีความหมาย

### 4.2 ลูป "ข้อขัดแย้งตัวเลข" ขัดกับหลัก L1/L2

`MultiAgent_Brainstorming.md` มีลูป `F -->|พบข้อขัดแย้งตัวเลข| E`
ซึ่งแปลว่า **agent แต่ละตัวคำนวณเลขเอง** แล้วค่อยมาเถียงกันว่าใครถูก

ตามเอกสาร 04-frameworks/01 (กฎ L1/L2) เลขทุกตัวต้องมาจากโค้ดชุดเดียว
→ **ข้อขัดแย้งเชิงตัวเลขต้องเกิดขึ้นไม่ได้ตั้งแต่ต้น** สิ่งที่ agent ควรเถียงกันคือ
*สมมติฐาน* (เช่น ควรใช้ discount rate เท่าไร, ควรตั้ง EPC เท่าไร) ไม่ใช่ผลลัพธ์เลขคณิต

**ข้อเสนอแก้ไข**: เปลี่ยนลูปเป็น "ข้อขัดแย้งเชิงสมมติฐาน/กลยุทธ์" แล้วให้โค้ดคำนวณใหม่
ทุกครั้งที่สมมติฐานเปลี่ยน — ได้ทั้งความถูกต้องและประหยัด request

### 4.3 ไม่มีเกณฑ์วัดว่าระบบทำงานดีพอหรือยัง

Blueprint บอกว่าจะทำอะไร แต่ไม่ได้บอกว่า **แค่ไหนถึงเรียกว่าใช้ได้** ไม่มี:
ความแม่นขั้นต่ำของการ parse, ตัวเลข calibration, อัตรา error ที่ยอมรับได้

→ เติมด้วยเกณฑ์จากเอกสาร 02 (p, Wilson CI, Brier, ECE ≤ 0.05) และวัดด้วย harness ที่มีแล้ว

### 4.4 ความเป็นส่วนตัวของ Stage 1

Stage 1 ส่ง **บทสนทนาลูกค้า / transcript การประชุม** เข้าโมเดล
ถ้าใช้ผู้ให้บริการฟรีแบบ anonymous ข้อมูลนี้ออกนอกองค์กรโดยไม่มีสัญญารองรับ

→ ต้องมีขั้น **redact ก่อนส่ง** (ชื่อ เบอร์ ที่อยู่ ชื่อบริษัท) หรือใช้โมเดลในเครื่องสำหรับ Stage 1 เท่านั้น

### 4.5 Learning Loop ยังเป็นแค่ชื่อ

Stage 5 เขียนว่า "log win/loss แล้ว refine prediction weights" — แต่โมเดลฟรีที่เรียกผ่าน API
**ปรับ weight ไม่ได้** ทำได้แค่ RAG/few-shot (ตรงกับที่เอกสาร governance ระบุไว้)

→ เปลี่ยนเป้าหมายเป็น: เก็บ win/loss เพื่อ (ก) ปรับ **ค่าคงที่ในสูตร** เช่น EPC จริงตามขนาดงาน
(ข) เป็นชุดทดสอบเพิ่มสำหรับวัด p (ค) เป็นตัวอย่าง few-shot — ไม่ใช่ fine-tune

## 6. สิ่งที่ Blueprint ทำได้ดีและควรรักษาไว้

- **Auto-Correction ที่ผูกกับเกณฑ์ธุรกิจ** (payback > 5 ปี → เสนอทางเลือกอัตโนมัติ) เป็นกลไกที่ตรงจุด
- **Human-in-the-Loop ก่อนส่งลูกค้า** — สอดคล้องกับชั้น L3
- **แยก parsing ออกจาก simulation ออกจาก financial** — เข้ากับ L1/L2 ได้พอดี ไม่ต้องรื้อ
- **ค่าตั้งต้นเป็นตัวเลขจริง** (22 บาท/วัตต์, 4.7 บาท/หน่วย) ทำให้ทดสอบซ้ำได้ ไม่ใช่ข้อความลอย ๆ

## 7. การตัดสินใจที่ลงมือแล้ว — พารามิเตอร์การเงินแก้ไขได้ (2026-08-23)

**เหตุผลของผู้ใช้**: พารามิเตอร์การเงินเปลี่ยนแปลงเป็นปกติตามภาวะตลาดและนโยบายบริษัท
การฝังค่าคงที่ไว้ในโค้ดจึงผิดตั้งแต่ต้น ไม่ใช่แค่เรื่องเลือกเลข 6.5 หรือ 8

**สิ่งที่ทำในแอป** (`assets/index.html`): เพิ่มกล่อง "พารามิเตอร์การเงินและวิศวกรรม (แก้ไขได้)"
พร้อมปุ่มคืนค่าเริ่มต้น

| พารามิเตอร์ | ค่าเริ่มต้น | เดิมฝังไว้ที่ไหน |
|---|---|---|
| Discount rate | **6.5%** | `calcNPV(cf, r=0.08)` |
| อายุโครงการ | 25 ปี | `for (y=1; y<=25)` สองจุด |
| Degradation | 0.5%/ปี | `saving *= 0.995` |
| O&M | 1.0% ของ EPC/ปี | `opex_ratio=0.01` |
| PSH | 5.0 ชม./วัน | `hoursPerDay = 5.0` |
| Performance Ratio | 80% | `PR = 0.80` |

### บั๊กที่เจอระหว่างทำ (สำคัญกว่าตัวฟีเจอร์เอง)

พอทดสอบว่าเปลี่ยนค่าแล้วผลเปลี่ยนจริงไหม พบว่า **เปลี่ยน PSH แล้ว NPV ไม่ขยับเลย**

สาเหตุ: ไฟล์ต้นฉบับคำนวณผลผลิตไว้ **สองที่ด้วยสูตรคนละแบบ**
- Stage 1 (ตัวเลขที่แสดงผู้ใช้): `PSH × PR × 365`
- สูตรการเงิน (ตัวเลขที่ใช้คิดเงิน): `kWp × 1450` ← ค่าคงที่ ไม่ผูกกับอะไรเลย

ที่ค่าเริ่มต้นทั้งสองเกือบเท่ากัน (1460 vs 1450) ความผิดพลาดจึงถูกกลบไว้ 0.7%
แต่พอผู้ใช้แก้ PSH เป็น 4.5 ระบบจะแสดงผลผลิตลดลง แต่ยังคิดเงินด้วยค่าเดิม

**แก้แล้ว**: ผลผลิตต่อ kWp มาจากสูตรเดียวทั้งระบบ ตรวจสอบด้วยการทดสอบ:

| ตั้งค่า | ผลิต/ปี | NPV | IRR |
|---|---|---|---|
| default (6.5%, PSH 5.0) | 1,553,440 kWh | 58.55 ล้าน | 29.5% |
| discount 8% | 1,553,440 kWh | **48.55 ล้าน** | 29.5% |
| PSH 4.5 | **1,398,096 kWh** | **41.10 ล้าน** | **26.3%** |

**บทเรียนเชิงระบบ**: ค่าคงที่ที่ถูกเขียนซ้ำสองที่ = บั๊กที่รอเกิด — ตรงกับหลัก L1 ในเอกสาร
