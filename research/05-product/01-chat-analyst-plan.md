# 01 — แผน: Chat Analyst ที่ใช้ได้กับงานทุกด้าน (ไม่ผูกกับโซลาร์)

> 2026-08-23 · ต่อยอดจากเอกสาร 01–04 ทั้งหมด · ลำดับงาน: **mockup web → ทดสอบ → APK**

## 1. โจทย์

เปลี่ยนจาก "แอปคำนวณโซลาร์" เป็น **ผู้ช่วยวิเคราะห์แบบแชท** ที่รับโจทย์ธุรกิจเป็นภาษาคน
แล้วตอบด้วยตัวเลขที่ตรวจสอบได้ — ใช้ได้ทั้งงานโซลาร์ การตลาด การขาย และการเงิน

## 2. หลักการที่ห้ามละเมิด (มาจากเอกสารก่อนหน้า)

| # | หลักการ | ที่มา |
|---|---|---|
| 1 | **โมเดลห้ามคำนวณ** — เลขทุกตัวมาจากโค้ด | 04-frameworks/01 · หลักฐาน: โมเดลตอบ 100,000÷5 = 2000 |
| 2 | เลขต้องมาจาก **แหล่งเดียว** ห้ามเขียนสูตรซ้ำสองที่ | บั๊ก PSH/1450 ใน v1.0.6 |
| 3 | **ข้อมูลไม่ถึงเกณฑ์ = ไม่ให้ตัวเลข** บอกว่าขาดอะไรแทน | 04-frameworks/01 ข้อ 3 |
| 4 | ความมั่นใจต้อง **calibrate** ก่อนแสดงเป็น % | 01-theory/02 |
| 5 | **ผู้ใช้แก้พารามิเตอร์ได้เสมอ** | การตัดสินใจ 2026-08-23 |
| 6 | ทุกคำตอบต้อง **ตรวจย้อนได้** ว่าใช้สูตรอะไร ค่าอะไร | DMAIC ขั้น Control |
| 7 | ค่าเริ่มต้นออฟไลน์ · โหมด AI เป็นทางเลือกเสริมที่ผู้ใช้เปิดเอง | ผลวัดผู้ให้บริการฟรี |

## 3. สถาปัตยกรรม 3 ชั้น

```
ผู้ใช้พิมพ์โจทย์
      │
      ▼
[L2] Router + Extractor ──── กฎ (ตอนนี้) → LLM ensemble (ภายหลัง)
      │  เลือกวิธี · ดึงพารามิเตอร์ · เดาค่าที่ขาด
      ▼
[Gate] ข้อมูลพอไหม / สมมติฐานผ่านไหม ──✗──► ถามกลับ ไม่ให้ตัวเลข
      │ ✓
      ▼
[L1] Compute Engine — สูตรเดียว ตรวจสอบได้ มี unit test
      │
      ▼
[L3] แสดงผล + ให้ผู้ใช้แก้พารามิเตอร์ + คนตัดสินใจ
```

**จุดสำคัญ**: L2 เป็นชั้นที่ *สลับได้* — วันนี้ใช้กฎ (rule-based) พรุ่งนี้เปลี่ยนเป็น LLM ensemble
โดยไม่ต้องแตะ L1 เลย ทำให้ทดสอบเทียบกันได้ตรง ๆ ว่าโมเดลช่วยได้จริงแค่ไหน

## 4. ทะเบียนวิธีคำนวณ (Method Registry)

แต่ละวิธีต้องประกาศ 4 อย่าง: พารามิเตอร์ที่ต้องการ · เกณฑ์ข้อมูลขั้นต่ำ · สูตร · หน่วยของผลลัพธ์

| วิธี | ใช้กับโจทย์ | เกณฑ์ขั้นต่ำ | สถานะใน mockup |
|---|---|---|---|
| `solar.sizing` + `finance.npv/irr` | ติดโซลาร์คุ้มไหม | ค่าไฟ + tariff | ✅ ทำงานจริง |
| `customer.ltv` | ลูกค้า 1 คนมีมูลค่าเท่าไร จ่ายค่า CAC ได้แค่ไหน | ARPU, retention, margin | ✅ ทำงานจริง |
| `price.ped` | ขึ้นราคาได้ไหม | ราคา–ยอดขาย ≥ 2 จุด | ✅ ทำงานจริง + สาธิต gate |
| `budget.allocation` | แบ่งงบยังไงให้คุ้มสุด | ROI ต่อช่องทาง + งบรวม | ✅ ทำงานจริง (LP แบบง่าย) |
| `churn.logistic` · `forecast.arima` · `sales.cox` | ทำนาย | ต้องมีชุดข้อมูล (EPV ≥ 10) | ⏳ ต้องอัปโหลดไฟล์ก่อน |

## 5. สิ่งที่ mockup ต้องพิสูจน์

1. โจทย์ภาษาคน → ตัวเลขที่ถูกต้อง โดยไม่มีโมเดลคำนวณเลย
2. **gate ทำงานจริง** — พิมพ์โจทย์ที่ข้อมูลไม่พอ ต้องถูกปฏิเสธ ไม่ใช่ตอบมั่ว
3. พารามิเตอร์ทุกตัวแก้ได้ และแก้แล้วผลเปลี่ยนทันที
4. แผงตรวจสอบบอกได้ว่า **ค่าไหนมาจากผู้ใช้ ค่าไหนเป็นค่าตั้งต้น** และใช้สูตรอะไร
5. ความมั่นใจแสดงตามสถานะจริง — ยังไม่ calibrate ต้องเขียนว่ายังไม่ calibrate

## 8. เฟสถัดไป — AI chat ทั่วไป

**โจทย์**: ตอนนี้ระบบตอบได้เฉพาะโจทย์ที่ตรงกับ 4 เครื่องคำนวณ ถ้าถามอย่างอื่นจะบอกว่า
"ยังจับโจทย์ไม่ได้" — ต้องทำให้คุยได้ทั่วไปเหมือน AI chat ปกติ **โดยไม่ทิ้งหลักการเดิม**

### กติกาที่ยังต้องรักษาไว้

| # | กติกา | วิธีบังคับใช้ในโค้ด |
|---|---|---|
| 1 | คำตอบที่ผ่านเครื่องคำนวณ กับคำตอบจาก AI **ต้องแยกกันด้วยสายตา** | คนละสีกล่อง + ป้ายกำกับชัด |
| 2 | ตัวเลขจาก AI **ห้ามแสดงเหมือนตัวเลขที่คำนวณแล้ว** | ติดป้าย "ยังไม่ผ่านการคำนวณ" ทุกครั้ง |
| 3 | ถ้าโจทย์เข้าเงื่อนไขเครื่องคำนวณ **ต้องใช้เครื่องคำนวณเสมอ** ไม่ปล่อยให้ AI ตอบ | router ตัดสินก่อน AI |
| 4 | เปิดโหมด AI = ข้อมูลออกนอกเครื่อง **ต้องเตือนก่อนใช้ครั้งแรก** | dialog ยืนยันครั้งแรก |
| 5 | ความมั่นใจแสดงเป็น % ได้เมื่อ calibrate แล้วเท่านั้น | ใช้ผล p/φ ที่กำลังวัด |

### สิ่งที่ต้องแก้ทางเทคนิค

1. **CORS** — เรียก `api.llm7.io` จากหน้าเว็บโดยตรงอาจถูกบล็อก (เคยเจอกับ Anthropic API มาแล้ว)
   ต้องทดสอบจากเบราว์เซอร์จริง ถ้าไม่ผ่านมี 2 ทาง: ห่อเป็น APK แล้วเรียกจากฝั่ง Java (แบบเดิม)
   หรือใช้ proxy ของตัวเอง
2. **โมเดลที่ใช้ได้จริงมี 7 ตัว** และ **ยิงขนานไม่ได้** (rate limit รวมทั้งบัญชี)
   → ensemble ต้องเรียงคิว · ตอบช้ากว่า chat ทั่วไป · ต้องมี UI บอกความคืบหน้า
3. **โมเดลหายกลางคัน** → ต้อง probe ก่อนใช้ และ fallback อัตโนมัติเมื่อเจอ 400/429
4. **ความยาวบทสนทนา** — โมเดลฟรีมี context จำกัด ต้องตัด/สรุปประวัติเมื่อยาวเกิน
